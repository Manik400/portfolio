Sustaining 500 events per second on a 400-camera video-analytics platform: event-specific topics, dead-letter isolation and streaming exports

Manik Goyal11 Software Engineer · Backend & Distributed Systems · Gurugram — I2V Systems, Gurugram, India · manikgoyal400@gmail.com
Abstract.

I work on a video analytics platform watching 400+ cameras across 200+ servers — ANPR, face recognition and intrusion events, all of it arriving faster than any single service wants to handle it. My job is making that traffic land correctly: event-specific Kafka topics with dead-letter handling, TimescaleDB that ingests instead of choking, exports that stream instead of dying.

Every line below is a before and an after on a system with real users on it. No estimates.

2Method

2.1 Topic partitioning with dead-letter isolation

Split one overloaded pipeline into event-specific topics with dead-letter handling, so a poisoned ANPR message stops blocking face and intrusion events instead of stalling all three.

throughput(t) = Σk∈{anpr,face,intr} consumek(t) , failed(m) → DLQk ⇒ replayable

2.2 Streaming export

Rebuilt the export around streaming reads and incremental batches. The out-of-memory failures on large ranges stopped with it.

2.3 Time-series ingestion

TimescaleDB hypertables with native compression, retention policies and composite indexes — sized for what 400 cameras actually push, not what a demo pushes.

2.4 Vector index footprint

Face enrollment, watchlist matching and deduplication on Milvus / pgvector — re-tuned the index so it fits the box, with match accuracy held.

5Related work (own)

The Streamer [1]. Sub-200 ms camera playback for live and recorded sources, decoding and remuxing H.264 in C++17 over FFmpeg. Moved transport off WebSocket streaming onto WebRTC/RTP with libdatachannel, adding HTTP signaling plus seek, pause and playback-speed controls over the data channel.

ParkNest [2]. Two-sided marketplace: host listings, renter bookings and prepaid credit settlement on .NET 8, PostgreSQL and a React front end. Optimistic-concurrency booking safeguards and an idempotent credit ledger that hold under overlapping requests — the interesting half of the problem.

7Discussion

I like the fixes that are structural — a pipeline split by event type instead of a bigger consumer, a streaming export instead of a larger heap, an idempotent ledger instead of a retry guard.

The rest is the surface and the substrate: Angular and React libraries that ten apps depend on, and, when the problem drops below the service layer, C++ and FFmpeg pushing frames over WebRTC.
